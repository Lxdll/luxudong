个人网站上的 AI 助手不是一个通用聊天机器人。它的任务非常具体：替我介绍自己的经历和项目，帮助访客查找博客，并让每个结论都能回到公开资料中的真实来源。

这个项目也不是把简历塞进 Prompt 后直接调用大模型。为了让回答可追溯、可更新、可降级，我把它拆成了知识准备、索引、混合检索、受约束生成、流式交互和安全控制几个独立部分。

本文记录的是截至 2026 年 7 月 23 日代码中已经实现的版本，包括本地调试中遇到的问题和最后采用的取舍。

## 先明确边界：这是 RAG，不是模型微调

这里没有训练一个新的模型，也没有对 Qwen3 做 Fine-tuning。所谓“让 AI 学会我的资料”，实际由下面几件事完成：

1. 将个人档案、职业经历和项目整理为结构化知识。
2. 将博客和长文本按标题层级切成较小片段。
3. 为片段生成 Embedding 并建立向量索引。
4. 同时保留关键词检索，弥补纯语义检索对专有名词和文章标题的不足。
5. 将检索结果作为“资料”交给生成模型，并限制模型只能根据资料回答。
6. 在证据不足或模型不可用时拒绝猜测。

这套方式的价值是：资料更新后只需要重新索引，不需要重新训练模型；每个回答也能附带真实的文章、经历或项目链接。

## 整体架构

![鲁旭东个人网站 AI 助手 RAG 系统流程图](/blog/personal-ai-assistant-rag.svg)

[下载可编辑的 Excalidraw 源文件](/blog/personal-ai-assistant-rag.excalidraw)

系统分成两个运行单元：

- 个人网站继续由 React 应用负责展示，部署方式不因 AI 功能改变。
- AI 接口运行在独立的 Cloudflare Worker 中，模型推理、向量查询和知识检索不会占用网站 VPS。

核心服务包括：

- **Workers AI**：运行 Qwen3 Embedding 和 Qwen3 生成模型。
- **Vectorize**：保存 1024 维向量，负责语义召回。
- **D1**：保存知识片段、全文检索数据、索引状态和匿名用量汇总。
- **Turnstile 与 Rate Limiting**：保护公开聊天接口。
- **Directus**：生产博客内容来源。
- **本地 MDX**：开发环境和 CMS 不可用时的博客来源。

## 前端：全站可用，但不打断原有页面

AI 助手挂载在路由外层，因此首页、职业经历、项目和博客页面都可以打开它。

桌面端是宽度约 420px 的右侧抽屉，移动端切换为全屏底部面板。视觉继续使用网站原有的黑白工牌风格，只用荧光绿表示 AI 状态。

交互上已经实现：

- “介绍一下鲁旭东”“他做过哪些 AI 探索”等快捷问题。
- SSE 流式显示回答。
- 回答来源卡片，可跳转到博客、职业经历或项目。
- “这条回答如何生成”面板，展示模型、检索模式、命中数量、耗时和索引时间。
- 停止生成、清空会话、Esc 关闭和 Tab 焦点循环。
- 生成期间的状态反馈和失败提示。
- Turnstile 验证。

浏览器只把当前标签页的会话写入 `sessionStorage`。标签页关闭后，会话不会成为长期记忆，也不会同步到其他设备。

前端是否显示入口由三个构建变量共同决定：

```text
VITE_AI_ASSISTANT_ENABLED
VITE_AI_API_URL
VITE_TURNSTILE_SITE_KEY
```

开发环境可以关闭 Turnstile Site Key 并使用本地 bypass；生产构建则必须同时具备 API 地址和 Turnstile 配置。

## Worker API 与一次对话的生命周期

Worker 对外提供四个接口：

- `POST /v1/chat`：聊天与流式回答。
- `GET /v1/meta`：模型、文档数、片段数和索引时间。
- `GET /health`：健康检查。
- `POST /internal/reindex`：Bearer 密钥保护的知识重建入口。

收到 `/v1/chat` 请求后，Worker 会先完成输入和安全检查：

1. CORS 只允许配置中的生产域名和本地开发地址。
2. 请求体不能超过 20KB。
3. 单条消息会清理控制字符并截断到 500 个字符。
4. 服务端最多接受最近 12 条消息，生成 Prompt 时只保留最近 6 条历史消息。
5. Turnstile 必须验证通过，本地开发可以显式 bypass。
6. 匿名访客令牌经过清洗后进入 Rate Limiter，当前限制为每分钟 6 次。

校验通过后，Worker 会立刻发送第一条 `metadata` 事件，而不是等检索和模型全部完成后才返回响应。这一点直接影响“点击发送后有没有反应”的体验。

完整 SSE 事件顺序是：

```text
metadata → metadata → delta... → sources → done
```

第一条 `metadata` 表示管线已经启动；第二条包含实际选择的检索模式。回答文本通过一个或多个 `delta` 传输，来源与最终耗时分别通过 `sources` 和 `done` 返回。异常时使用 `error` 事件。

## 知识库：页面与 AI 共用同一份个人资料

个人资料保存在 `content/knowledge.json`，内容包括：

- 中英文个人简介。
- 技能和当前关注方向。
- 职业经历。
- 项目经历。
- 对应的站内与 GitHub 链接。

网站的职业页面和项目页面直接读取这份数据，Worker 建立个人知识索引时也读取同一份数据。这样可以避免页面已经更新、AI 仍在使用旧简历的问题。

知识校验会扫描“待补充”“TBD”“TODO”等占位内容。严格模式下只要存在占位字段，生产索引和部署就应该停止。

博客有两种来源：

- Directus 中对外可访问的文章。
- 仓库中的本地 MDX 文章。

本地 MDX 不只是展示备用内容，也会进入 Worker 的 bundled knowledge，确保 CMS 暂时不可用时仍然能找到文章。

## 标题感知切分与增量索引

长文不是整篇生成一个向量。切分器会识别一级到三级标题，并保留：

- 来源 ID 和类型。
- 文章标题与当前章节标题。
- 分类、发布日期和 URL。
- 片段内容。
- SHA-256 内容哈希。

当前切分目标约为 300–800 个字符，并在长片段之间保留少量重叠。较短的相邻章节会在不超过上限时合并，避免生成大量缺少上下文的碎片。

片段 ID 中包含内容哈希的前 12 位。每次重建时，索引器会：

1. 生成当前全部片段及哈希。
2. 与 D1 中的旧哈希比较。
3. 只为新增或变化的片段调用 Embedding。
4. 将新向量写入 Vectorize，同时更新 D1 和全文索引。
5. 删除已经不存在的 D1 片段和 Vectorize 向量。
6. 更新最后索引时间和博客来源状态。

Worker 的 Cron 在每小时第 17 分钟执行一次同步，部署流水线也会在 Worker 发布后调用受保护的重建接口。

## 检索：语义与关键词并行

普通经历、项目或博客问题会同时进入两条检索通道。

### 语义检索

问题先通过：

```text
@cf/qwen/qwen3-embedding-0.6b
```

生成 1024 维查询向量，再由 Vectorize 取回语义最接近的 8 个片段。

语义检索适合处理表达方式不同但含义相近的问题，例如“他如何把 AI 用到真实产品中”，不要求问题必须包含知识库里的原词。

### 关键词检索

D1 同时执行关键词检索：

- 英文和技术词优先使用 FTS5 与 BM25。
- 中文会提取重点短语、前后缀和双字组合，再通过 `LIKE` 召回并计算命中权重。

这部分是在本地调试中专门补强的。SQLite 的 `unicode61` tokenizer 不会像中文分词器一样自然拆分句子，如果只依赖 FTS，诸如“合同编辑器”这类问题很容易被完整长句稀释。

关键词检索特别适合：

- 精确文章标题。
- React、RSC、MQTT 等技术名词。
- “合同编辑器”“磐石系统”等项目专有词。

### RRF 融合与来源去重

两路结果各取前 8 条，再使用 Reciprocal Rank Fusion 合并：

```text
score += 1 / (60 + rank)
```

RRF 不要求语义分数和 BM25 分数处在同一量纲，只根据两边的排序位置融合。之后每个来源最多保留两个片段，最终最多把 5 个片段交给生成模型。

当前相关度门槛为：

- 语义分数至少 `0.42`，或
- 关键词分数至少 `0.2`。

对外的来源卡片还会按来源 ID 再去重，避免一篇长文章因为命中了两个章节而显示两张相同卡片。

## 为什么“你是谁”不走普通 RAG

“你是谁”“介绍一下鲁旭东”是最基础、也最不应该依赖远程模型稳定性的问题。

最初版本把“你是谁”当成普通检索问题，本地 Workers AI 发生上游超时时，用户会长时间看不到回答。现在这类问题会先经过身份意图识别，然后直接读取 D1 中 `profile:overview` 的结构化档案。

回答由经过校验的资料确定性生成：

> 我是鲁旭东的 AI 助手，会根据他的公开个人资料、项目和博客回答问题。

接下来才是鲁旭东的职业定位和经历简介。这样既不会让 AI 冒充真人，也不会为了一个固定事实调用 Embedding 和大模型。

这条路径的模式会在前端显示为“结构化档案直答”，正常情况下可以在几十毫秒内返回。

## 受约束生成与提示注入防护

只有在检索结果通过相关度门槛、Embedding 可用且当天生成次数没有超过软上限时，Worker 才会调用：

```text
@cf/qwen/qwen3-30b-a3b-fp8
```

系统 Prompt 明确要求：

- 它是鲁旭东的 AI 助手，不是鲁旭东本人。
- 只能根据提供的公开资料回答。
- 未知信息必须明确说明不知道。
- 不得伪造链接或个人事实。
- 中文问题中文回答，英文问题英文回答。

检索内容会先转义 HTML 特殊字符，再包裹在独立的 `<source>` 节点中。Prompt 同时声明来源是“不可信的参考资料”，不得执行博客正文中出现的任何指令。

这不能替代完整的安全评测，但至少把“资料”和“系统指令”分成了两个明确的信任层级。

## 超时、额度与降级

个人网站助手不能因为模型偶发不可用就一直 Pending。

当前设置：

- Embedding 超时：8 秒。
- 生成启动或流式读取超时：12 秒。
- 每日生成软上限：默认 150 次。

Embedding 失败后，系统会停止尝试生成模型，直接使用 D1 关键词结果：

- 有相关结果：返回匹配的资料摘要和链接。
- 没有足够证据：明确拒答，不猜测个人事实。

如果生成模型在已经找到资料后失败，也会回退到来源列表。降级模式仍然保留 `sources` 和 `done` 事件，因此前端不需要切换另一套协议。

## 隐私、滥用控制与可观测性

服务端不会把问题、回答或完整对话写入 D1。持久化的数据只有：

- 公开知识片段。
- 索引状态。
- 每日检索次数、生成次数和错误次数。

结构化日志会记录请求 ID、耗时、召回数量、是否使用 Embedding 和当前模式，但不会主动记录问题正文。

公开接口还有三层控制：

- Turnstile 验证访客。
- 每个匿名访客每分钟最多 6 次请求。
- 全局每日生成软上限，超过后进入只检索模式。

## 本地开发中最容易误判的三个问题

### 1. 访问 `http://localhost:8787/` 返回 404

这是预期行为。Worker 没有首页路由，应该访问：

```text
http://localhost:8787/health
http://localhost:8787/v1/meta
```

聊天接口是 `POST /v1/chat`，不能直接在地址栏中用 GET 验证。

### 2. 本地请求长时间 Pending

Workers AI 和 Vectorize 在本地开发时仍访问远程资源。本地代理、Cloudflare 上游推理或绑定配置异常都可能导致等待。

解决方式不是无限延长超时，而是：

- SSE 建立后立刻返回 metadata。
- 给 Embedding 和生成阶段分别设置超时。
- 保留 D1 关键词降级。
- 把稳定的身份介绍从模型链路中拆出来。

### 3. 网站没有 AI 入口

入口是否显示不仅取决于组件是否挂载，还取决于构建变量。开发环境至少需要：

```text
VITE_AI_ASSISTANT_ENABLED=true
VITE_AI_API_URL=http://localhost:8787
```

修改环境变量后需要重新启动 Vite，因为它们会在构建时注入。

## 部署与质量门禁

GitHub Actions 将网站与 Worker 分开验证：

- 网站执行知识校验、ESLint 和生产构建。
- Worker 执行 TypeScript 类型检查和 Vitest。
- AI 功能开关开启时，流水线才部署 Worker。
- 部署后自动执行 D1 migration、知识重建、健康检查和 `/v1/meta` readiness 检查。
- 最后才构建并部署包含 Worker 地址的前端镜像。

仓库中维护了 32 条中英文评测问题，覆盖：

- 个人介绍、技能、经历和项目。
- 精确博客标题与模糊主题。
- 中英文问答。
- 未公开薪资、兴趣和隐私信息。
- 提示注入请求。

目前自动化测试已经覆盖切分、占位内容校验、RRF、来源限制、身份意图、超时和来源去重。32 条评测集当前主要用于约束样本结构；真正的 `Recall@5`、链接准确率和首字延迟仍需要在部署后的真实 D1、Vectorize 和 Workers AI 环境中持续执行，不能只靠单元测试宣布达标。

## 这个项目体现的不是“接了一个模型”

真正花时间的部分不是调用一次大模型 API，而是处理模型之外的工程问题：

- 如何让页面和知识库使用同一份真实资料。
- 如何让中文专有词在全文检索中可靠命中。
- 如何融合两种分数体系不同的检索结果。
- 如何防止模型把博客正文当成指令。
- 如何在免费额度、上游错误和本地代理异常时仍给用户结果。
- 如何让答案附带可验证来源，而不是只提供一段听起来合理的话。

对个人网站而言，这套架构已经足够小，也保留了继续扩展的空间。下一步重点会放在真实索引上的检索评测、Directus 发布流程自动化，以及对低相关度问题更细致的博客推荐策略上。
